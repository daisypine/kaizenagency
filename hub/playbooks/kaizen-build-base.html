Kaizen Build Base

Every new Kaizen client site is cloned from the Kaizen Base site, not built from scratch. The base is permanently noindexed and password-protected and never belongs to a client. WordPress + Elementor is settled; do not suggest a different platform.

This skill owns the technical path from clone to handback. Copy and content standards live in kaizen-copy-doc. This skill is self-contained on purpose so it works in any chat or Project; a longer process doc may exist in Daisy's Kaizen Project or Drive, but never block on it.

Rough timings, so a day can be planned: clone-reset 30-45 min · migration 15-45 min depending on site size · DNS zone build 30 min · launch-day cutover 1-2 hrs including propagation · Complianz wizard 15 min · analytics and Search Console 30 min · post-launch audit 20 min · handback 15 min.

Before cloning: signed agreement + cleared deposit, and the sitemap signed off. If either is missing, stop and ask Daisy.

How to verify anything (read this first)

The expensive mistakes on a Kaizen launch are rarely wrong actions. They are wrong verifications, and they compound: one bad conclusion becomes the lens for every symptom after it. Four rules:

  1. Check the live site from outside the browser you have been working in. A build browser carries sessions, caches and redirects no visitor has. An external redirect checker, or a phone on cellular, is the only honest test of "is it up".

  2. Vary the URL on every re-check. Fetchers and DNS lookup tools cache per URL for minutes. Re-running an identical check returns your own stale answer, indistinguishable from "nothing changed yet". Add a throwaway query parameter.

  3. A direct reading beats an inference. If a settings field says X and your theory says it secretly means Y, the field is right. Test the theory before building anything on it.

  4. Re-read state after every UI action. Count the rows, re-fetch the page, confirm the value. Several WordPress and Elementor controls fail silently and still look like they worked.

Fetch the front end logged out. An admin-session fetch includes the admin bar and plugin notices, so a scan for third-party domains picks up Wordfence, Code Snippets and PageSpeed URLs that no visitor ever loads. Use a credential-less request before concluding anything about what the public site contains.

A failed fetch() does not mean a site is down. Browser fetch() is subject to CORS, and www.clientdomain.com is a different origin from clientdomain.com. Running fetch('https://www.clientdomain.com/') from a page served on the apex fails every time, on a perfectly healthy site, and the error looks identical to the server being unreachable. This has already produced a false "www is broken" alarm and an invented SSL problem on a site whose wildcard cert was fine. To test a hostname, navigate to it and read the resulting address bar, or use a server-side fetch. Only trust a scripted fetch when it is same-origin.

Scripted checks are only as good as their selector. Before reporting that something is absent, confirm the selector finds anything at all on a page where you know it exists. A scan of input[type=checkbox] on a Complianz screen, or of top-level widget settings on an Elementor page, returns an empty list that reads as "clean" when it actually means "looked in the wrong place".

Clone reset (30-45 min)

Run immediately after cloning, before any build work:

  1. Site title, tagline, admin email, timezone, date format, language, site icon. Timezone is the one people skip: a base clone often carries UTC+0, which throws every post date, scheduled publish and form-notification timestamp off by 7-8 hours for a California client. Set America/Los_Angeles and confirm "Local time" reads correctly before moving on.

  2. Create a named Administrator account for each person on the build, then delete the base admin account (otherwise every client site shares one login)

  3. Regenerate security keys/salts; re-save permalinks

  4. wp search-replace '<old>' '<new>' --dry-run, then run it for real

  5. Then wp elementor replace-urls <old> <new> (plain search-replace misses Elementor data)

  6. Elementor > Tools > Regenerate CSS & Data, then purge SG Optimizer cache (it will keep serving old URLs otherwise)

  7. Deactivate and reactivate Elementor Pro and Unlimited Elements against this site's own seat

  8. Check for carried-over tracking: Complianz Statistics settings, any GA4/GTM ID, header/footer code. Remove anything not belonging to this client

  9. FluentSMTP credentials swapped to this client's sender; form notification addresses repointed; send one test submission per form and confirm it lands (check junk)

  10. AIOSEO site name, organisation details, social profiles

  11. Confirm Discourage search engines is still ON

  12. Confirm staging password protection is ON (SiteGround Site Tools > Protected URLs). This is what actually keeps staging out of Google; Discourage search engines is only advisory. If you ever drop one, keep the password

  13. Delete AI Agent by SiteGround if it reappeared

  14. Add team members at their roles: Daisy admin + hosting owner; Basil admin, no hosting access; developer admin for the build only (downgrade at hand-back); designer no WordPress account; SEO/content Editor; client nothing until after launch

Security audit: run on any site Kaizen did not build alone (15 min)

Run this on any site an outside contractor touched, any site inherited from another agency, and once before every launch. A compromised site migrates perfectly - the copy carries the backdoor with it - so audit the SOURCE before migrating, not the destination after.

The hidden-admin check, which is the highest-value one minute in this whole skill. Open wp-admin/users.php and compare the filter count against the item count. "All (2)" next to "3 items" means a user is being hidden from the list. Visit wp-admin/user-edit.php?user_id=N directly to see a hidden account. Tells:

  • An email on a domain that cannot receive mail (.invalid, .local, .test)

  • A generic job-title username (content_operator, wp_support, seo_manager)

  • Administrator role, zero posts, no name, no bio

Concealment is usually PHP injected into a legitimate plugin's own file - clean, unobfuscated, hardcoding a user ID into pre_get_posts and template_redirect. Malware scanners that diff against the WordPress.org repo cannot catch it in a PREMIUM addon, because there is no public copy to diff against.

Also check: Code Snippets entries, wp-content drop-ins (only advanced-cache.php and object-cache.php are expected from SG Optimizer), mu-plugins, and theme functions.php.

Then rotate every credential - WordPress admins, hosting, FTP/SSH, database - and remove contractor accounts. A contractor who was themselves breached hands the attacker access to every site that contractor touched, so scope the sweep by "which sites did they work on", not "which sites do we own".

Re-run the count check at handback, and turn on Wordfence 2FA for every remaining admin. Wordfence's "Prevent discovery of usernames through '/?author=N' scans, the oEmbed API, the WordPress REST API, and WordPress XML Sitemaps" is ON by default - confirm rather than assume, but don't spend time re-enabling it.

Host malware quarantine: deleting the plugin is not enough

When SiteGround flags a file it changes its permissions to non-executable and starts a 3-day clock. Critically: WordPress can no longer delete those files. Deleting the plugin from the admin appears to work - it vanishes from the plugin list - but the directory stays on disk, the next scan re-flags it, and the warning escalates.

So after removing any flagged plugin: open Site Tools > Site > File Manager and confirm the directory is really gone from public_html/wp-content/plugins/. Delete it there if it is still present. Only then request the rescan, via Client Area > Home > Important Notifications > Review > MORE ↓ > Request Scan (it is in the dropdown, not one of the three main buttons).

The incident panel's evidence list does not refresh after a rescan - do not read a stale entry as proof the file is still there, or its absence as proof it is gone. The filesystem is the only reliable check. Read the incident text rather than the red banner: the banner says "temporarily suspended" as boilerplate while the incident is often still inside a 3-day grace period, which is a very different level of urgency.

Moving a site between hosts or domains (15-45 min)

If both sides are on SiteGround, use SiteGround Migrator. Free, pulls server to server with no size cap, and rewrites URLs on the way in. Site Tools > WordPress > Migrator on the DESTINATION generates a token; install the SiteGround Migrator plugin on the SOURCE and paste it there.

Kaizen also owns an All-in-One WP Migration licence (Unlimited Extension; the billing receipt is in Daisy's personal Gmail, not the agency account). Use it when the source is NOT on SiteGround, when the Migrator fails, or when a portable .wpress file is wanted as a backup artifact.

Before any migration:

  • Run the security audit above on the SOURCE. A migration copies a compromise faithfully

  • Deactivate Broken Link Checker on the source. It bloats the database with its own tables and is the first suspect when a migration stalls

  • Take a labelled backup on the source

  • Confirm the destination is empty; a migration overwrites it

After the migration lands:

  • Run clone-reset steps 6 through 10 against the new URL

  • Confirm Discourage search engines is still ON

  • Confirm Complianz survived and is active

  • Check the footer, contact blocks and form notification addresses for a rewritten email like info@<old-domain>

  • Release the Pro licences from the OLD location. Deactivate Elementor Pro and Unlimited Elements Pro on the source site, then remove that domain from both licence dashboards

  • Delete the SG Migrator plugin from both sites once the transfer is confirmed good

The SiteGround temp host: the biggest trap in this document

SiteGround gives the destination a hostname like 1792700227-xxxx.wp-transfer.sgvps.net. Understand exactly what it does, because getting this wrong takes a live site down.

  • The migration sets WordPress's Site Address and WordPress Address (Settings > General) to the temp host. Everything below follows from that one fact. The database is NOT on the real domain.

  • It rewrites the domain in output AND on input. Content typed into Elementor through the temp host is stored with the temp hostname substituted in. You can type jose@clientdomain.com, watch it save, verify it on screen, and still have jose@1792700227-...sgvps.net in the database. Verifying an edit through the temp host proves nothing.

  • Links built on the real domain - the Site Tools auto-login button, WordPress password-reset emails - 403 while DNS still points elsewhere. Swap the hostname for the temp domain and they work; reset keys live in the database and are not host-bound.

The failure mode, which is severe: once DNS moves to SiteGround, WordPress's canonical redirect sends every visitor from the real domain to the temp host, which then redirects to itself. http://domain → https://domain → https://temp-host → loop. The site is unreachable for everyone, and an external redirect checker is the only thing that shows it.

These symptoms are all the same bug, not separate ones. Do not explain any of them away as a browser cookie:

  • getting logged out of wp-admin on nearly every save

  • the front end returning ERR_TOO_MANY_REDIRECTS

  • the real domain bouncing to the temp host in any browser, including Incognito and on a phone

So before DNS cutover, always, in this order:

  1. Settings > General - set Site Address and WordPress Address to the real domain, typed by hand, never pasted from what is displayed

  2. Install Better Search Replace (free, WordPress.org) and replace <temp-host> → <real domain>. Dry run first. Elementor stores JSON so a string replace is safe, and the plugin handles serialised data too

  3. Run the replace from the real domain's wp-admin, never from the temp host - otherwise the rewrite puts the temp hostname straight back as it saves

  4. Re-crawl every page and grep the HTML for sgvps.net. Expect zero. It hides in the footer mailto:, in uploaded image URLs, and in the sitemap link in every page head

  5. Delete Better Search Replace

  6. Only now migrate the Unlimited Elements licence, and stop using the temp host entirely

Unlimited Elements enters safe mode after a migration, having spotted a duplicate install. Do not click "Migrate License" while on the temp hostname - it burns a seat on a host that dies in 48 hours and you will do it twice. Choose Duplicate Website, which keeps premium functionality for roughly two weeks, then migrate the licence once, at the real domain, after cutover.

DNS: build the zone BEFORE pointing nameservers (30 min)

When a client domain is added to SiteGround, SiteGround auto-creates its own mail configuration: MX at mx10/20/30.antispam.mailspamprotection.com, its own SPF TXT, a default._domainkey DKIM CNAME, and A records for mail, autoconfig and autodiscover.

Repoint nameservers with that default zone in place and all of the client's email routes to SiteGround instead of their real mail host.

In this order, every time:

  1. Inventory the CURRENT live zone - MX, SPF, DKIM selectors, DMARC, autodiscover, any verification TXT tokens, and the A/CNAME records

  2. Add the domain to SiteGround as its OWN website entry

  3. Delete every auto-created mail record listed above

  4. Recreate the real records exactly, including verification TXT tokens whose purpose nobody remembers - cheap to carry, expensive to lose

  5. Only then repoint nameservers at the registrar

  6. Verify with live DNS lookups that MX, SPF and autodiscover resolve correctly, then send a real test email both directions before calling it done

To move DNS control without touching the website, point the A records at the CURRENT host's IPs. Control transfers, the existing site keeps serving, and going live later is a one-record change.

Get the server IP from Site Tools > Dashboard > Site Information, not from memory or an old note. The Dashboard also shows "Your domain's A record is not pointed to this website" until it is - a free confirmation, though it lags behind real propagation because it reads a cached resolver.

Check for more than one A record on the apex. Hosts often run two in round-robin. Edit one and leave the other and roughly half of visitors land on the old site at random. Delete the spares FIRST, while the remaining record still points at the old host, then repoint what is left.

When checking propagation, change the query each time. Lookup tools and fetchers cache responses per URL for several minutes; re-running the identical query returns your own stale answer and looks exactly like "not propagated yet". Vary a parameter, or use a second resolver.

Pre-launch content and form audit (15 min)

Run this before the site is made indexable. Both of these have shipped live on a real Kaizen launch.

Grep every page in the sitemap for placeholder text. Fetch each URL logged out, strip tags, and count Lorem ipsum. Template pages that nobody rewrote - a Projects page, a leftover duplicate like /project-page/ - stay published and go straight into the sitemap. Decide per page: write real content, trash it, or noindex it. Do not leave the decision for after launch.

Read the actual field list of every form, from the rendered HTML, not from the Elementor canvas. Pull name, type, placeholder and required for each field. Things that look right in the editor and are wrong on the page:

  • a field still named form_fields[email] that has been switched to type="tel" with a "Phone" placeholder, so the form shows two identical required Phone boxes and captures no email address at all

  • a "Preferred contact method" option offering Email when there is no email input

  • a required field the client never meant to make required

The field name is the giveaway: it keeps the original field's id even after someone changes the type, so a [email] field of type tel is always a mis-edit. Send one real test submission per form and read what actually arrives.

Every content image gets alt text AND a description - no exceptions. Before a site goes indexable, list every image attachment from /wp-json/wp/v2/media?per_page=100&_fields=id,source_url,alt_text,caption,description,title (page through all of them) and fix any with an empty alt_text or empty description. Then crawl every page logged out and assert every <img> inside page content has a non-empty alt. Rules:

  • Alt text describes what is in the picture plus the service and city where true, in under ~125 characters: Two-story stucco home exterior repainted in San Jose. Never keyword-stuff, never "image of", never the filename

  • Description (the media library field) is one or two plain sentences on what the photo shows and which page or project it belongs to. It is what the team and future AI work read to reuse the photo correctly

  • Title is cleaned up from the filename (IMG_4432 → Westmont hallway repaint)

  • Never name a private homeowner, street address or person in alt text unless the client approved it

  • Purely decorative images (dividers, background shapes) get alt="" on purpose, but still get a description in the library

  • Elementor image widgets pull alt from the media library at render time, so fix the library entry, not the widget. Background images have no alt at all - if a photo carries meaning, it belongs in an image widget, not a section background

  • Set alt and description at upload, every time a photo is added, not as a later sweep. Write them through the REST API (POST /wp-json/wp/v2/media/{id} with alt_text, description, title) when uploading in bulk

Launch day (early morning, 1-2 hrs)

  1. Confirm Site Address and WordPress Address are the real domain, and the temp-host search-replace is done and verified at zero. If this is skipped, the cutover takes the site down - see the temp host section above

  2. Change only the A record and the www record. Check for an AAAA record pointing at the old host; leave MX, TXT (SPF, DKIM, DMARC), SRV and mail CNAMEs exactly as they are

  3. Wait for the TTL. Note it beforehand - a 14400s TTL means up to 4 hours where some visitors still reach the old site. Dropping the TTL to 300 a few hours ahead of the switch makes the cutover near-instant, and is worth doing whenever the old and new sites differ enough that a split audience matters

  4. Issue SSL for apex and www (SiteGround auto-issues a Let's Encrypt wildcard by DNS validation once its nameservers are in place - check Site Tools > Security > SSL Manager before assuming you need to do anything)

  5. Turn on Site Tools > Security > HTTPS Enforce. This is a separate server-level toggle and it is the step people skip: an active certificate does NOT redirect http to https on its own. Verify the toggle is on for the domain rather than inferring it from the certificate, and purge cache afterwards so no http pages stay cached

  6. Pick a canonical host (apex or www) and 301 the other to it. Default to the bare domain unless the client's print, email and Google Business Profile already use www. Whichever you pick, make the copy docs match - a doc that specifies www.clientdomain.com against a site that serves the apex quietly seeds the wrong URL into schema blocks and every future page

  7. Remove staging password protection

  8. Turn OFF Discourage search engines. A site that launches still noindexed ranks for nothing and nobody notices for weeks

  9. Check the other two places a noindex hides: AIOSEO > Search Appearance, and /robots.txt for a Disallow: /

  10. Purge cache

  11. Read the sitemap and delete what should not be in it. A clone that was not fully reset ships /hello-world/, /sample-page/, /category/uncategorized/ and /author/<admin-username>/ to Google the moment you make it indexable. The author archive is the worst of them: its page title is the administrator's username. Trashing the default post and page drops all four from the AIOSEO sitemap automatically. Rather than hiding the author archive, give every admin a non-obvious username at creation (they can sign in with their email address instead), and delete the agency account at handback

  12. Redirect map: if the client had an existing site, 301 its top URLs to the new equivalents

  13. Submit /sitemap.xml in Search Console; confirm GA4 is firing on the live domain; re-run the Complianz cookie scan

Then verify the launch from outside the build browser. Run the domain through an external redirect checker and confirm the chain is exactly http://domain → 301 → https://domain → 200, with no third hop. Then load it on a phone on cellular. A site is not "live" until that chain is clean - the build browser will happily show a working site that no visitor can reach.

48 hours later, run site:clientdomain.com in Google. Nothing at all means a noindex is still live somewhere.

Post-launch audit (2-3 days after launch, 20 min)

Launch day proves the site is reachable. This proves it is correct. Run it a few days after every launch, and again before sending any client progress report - a report that lists work done on a site with a dead phone link is worse than no report.

Everything below was found on a site that had already launched cleanly and looked finished.

Enumerate pages from the WordPress REST API, not the XML sitemap. /wp-json/wp/v2/pages?per_page=100&status=publish&_fields=id,link,title gives you IDs and URLs in one call. Fetching /page-sitemap.xml from inside a page context and regexing <loc> has returned zero matches on a sitemap that was fine, which reads as "no pages" and is badly misleading. Get the post count too: /wp-json/wp/v2/posts returning [] on a site whose nav has a Blog link is its own finding.

Then crawl every URL logged out and check:

1. Click-to-call links. Collect every a[href^="tel:"] and assert each one equals exactly tel:+1XXXXXXXXXX. Parentheses, spaces and encoded %20 break dialling on many phones, and local service sites convert mostly on mobile taps. One real site carried three different malformed formats at once - tel:(650) 362-4373, tel:+1 (650) 362-4373 and the encoded variants - across the header, the footer, six page bodies and four legal pages. 57 links, several broken, on a site that looked perfect. Leave the visible text in whatever human format the design uses; only the href has to be strict.

2. JSON-LD against the real business facts. Read the raw HTML for script[type="application/ld+json"] and actually read the values. A ContactPage block was telling Google Mon-Sat 07:00-17:00 while the footer and the client both said Mon-Fri 8-5 and Sat 8-2. Schema is what Google shows in results, so wrong hours there are worse than wrong hours in body copy, and nobody looks at it. Check openingHoursSpecification, telephone, @id and url - the URLs in schema often still carry the host the copy doc specified rather than the one the site actually serves.

3. Placeholder text. Re-run the Lorem ipsum grep. It comes back: a Projects page shipped with 13 instances and a giant LOREM IPSUM headline above a grid of real photos.

4. Nav items that go nowhere. Pull every nav and header link and flag any href="#" or empty href. A Blog item pointing at # sat in the main nav of a live site. Either ship the page or remove the item.

5. Internal 404s. Status-check every internal link found on the homepage and on each page. Also directly check any URL the footer or copy doc promises but that may not be built yet.

6. Consistency against the copy doc. Email address, phone, hours and business name, compared between the live site and the Designer+Dev doc. These drift: one site had info@ in the doc and jose@ live, and hours that disagreed between the footer, the estimate page and the schema.

7. Google Business Profile. Open it signed in as the managing account and confirm a website is actually attached - a profile showing "Add website" is the single highest-value fix available and is easy to assume was done. Check the profile name matches the licence, Yelp and the site exactly; a profile called "JDH Landscaping" against a business called "JDH Garden Services, Inc." is a NAP mismatch that costs local ranking. Note that GBP edits go into a pending review of up to ~10 minutes, and do not stack a name change, a website change and an hours change in one batch - make the important ones, let them land, then do the rest.

8. Staging is not indexed. Run site:staging-host in Google. A full copy of the client site indexed on a Kaizen staging subdomain competes directly with the live domain.

9. Image alt text and descriptions. Re-run the media library check and the <img alt> crawl from the pre-launch audit. Pages added after launch are where images ship without alt text - every new project, industry, city page and blog post must come back at zero missing.

Finally, re-run the whole crawl after the fixes and assert the counts, rather than assuming a template edit propagated. See the Elementor widget-ID trap below for why it often does not.

Adding pages to a live site (buildout and restructure)

Most post-launch SEO work is adding pages: industries, projects, city pages, service pages, blog posts. This is the order that worked on a real 25-page night (Sunwest Painting, Oct 2026), and the traps it hit.

Plan in the master sitemap first. One Google Sheet per client, in the client's Drive folder, named Sitemap - <Client> (Master), columns # | Section | Page | URL | Status | Month | Template | Owner | Notes. Status values: Live, Live - needs photos, In progress, Planned, Backlog, Dropped. Never keep a second sitemap or a status tab beside it - merge into the master and trash the duplicate. Update it the same night pages go live.

Facts come only from the client. Build a short copy brief first (business facts, banned claims, approved CTAs, URL map, project notes in the client's own words) and write every page from it. No invented stats, certifications, quotes or timelines; no written-up testimonials; no private homeowner names. Pages with thin facts are kept shorter rather than padded.

Hubs and children. When a single page sits at /industries/, /projects/ or /locations/, move it to a child URL (/industries/property-management-painting/) and build a hub at the original URL with a card grid linking every child. 301 nothing - the hub keeps the old URL alive.

Clone, don't rebuild. Copy an existing page's _elementor_data through REST (GET /wp-json/wp/v2/pages/{id}?context=edit), swap the text and image IDs in the JSON, then create the new page with template: 'elementor_header_footer' and meta _elementor_page_settings: {hide_title: 'yes'}. Set the SEO title and description with POST /wp-json/aioseo/v1/post {id, title, description}.

Internal links on every new page: up to its hub, across to 2-3 siblings, to 1 related project or service, and to the quote/bid page. Then go back and add links TO the new page from the existing pages that should mention it. A page nobody links to is invisible.

Nav. Add hubs as header dropdown parents with children under them (wp/v2/menu-items, parent = the hub item). WordPress menu items follow the page title unless given an explicit title, so renaming a page silently renames its nav item - always set the menu item title explicitly.

Drafts and links. A link to a draft page is a 404 for every visitor. Either publish together, or strip links to drafts and restore them on publish. Ask Daisy before publishing anything live; get the approval in words that match exactly what is going live.

After every batch: Elementor > Tools > Clear Files & Data, then Purge SG Cache, then crawl every new URL logged out: status 200, no Lorem ipsum, no href="#", all internal links 200, every image has alt text, JSON-LD reads right.

Traps from that night:

  • Better Search Replace edits can be overwritten. Elementor keeps its own copy of the content; opening the page in the editor afterwards can save the stale version back over the fix. Make text changes in Elementor JSON or the editor, not BSR

  • Element caching serves stale HTML after a REST write. Clearing Elementor files and data fixes it; the page is not broken

  • Hidden sections clone hidden. A section copied from a page where it is hidden on all devices (hide_desktop, hide_tablet, hide_mobile) stays invisible on the new page. Strip those flags when cloning, and flag the original to Daisy

  • Form notification emails default to "New message from WordPress". Set a real subject per form (New quote request - <Client> website) so leads are not filtered as noise

  • Social profiles (Instagram, Facebook) are the fastest source of real project photos and project ideas - crawl them before asking the client, and make sure they are linked in the footer and in schema sameAs

Testimonials and reviews

Never publish a written-up testimonial. Every quote on a client site must come from a real customer - a Google or Yelp review, or something the client can produce in writing. The FTC's fake-review rule carries civil penalties per violation. If a new site has no reviews yet, leave the section out.

When pulling from Yelp, use short excerpts with the reviewer's first name, last initial and city, link each one to the business's Yelp page, and pick quotes that cover different service lines rather than three versions of the same compliment. Republishing full review text is against Yelp's terms; a short attributed excerpt with a link back is the normal practice.

Check where the client's reviews already are before planning a review push. A business with 159 Yelp reviews at 4.5 stars and zero on Google does not have a reviews problem, it has a platform problem, and the fix is a review link in the client's hands rather than anything on the website. That comparison is also the most persuasive line you can put in a client report.

Legal pages and Complianz

Do not hand-write legal text, and do not launch a California client on placeholder text.

Know what the free tier actually does, because the plan matters here. On free Complianz, only the Cookie Policy, the consent banner and the Opt-out preferences page are generated. Privacy Statement, Imprint and Disclaimer are Premium - the wizard shows an "Upgrade" tag and only lets you point at an existing page. So a Kaizen site still needs its own Privacy Policy, Terms & Conditions and Accessibility Statement pages; the base ships Privacy Policy and Accessibility Statement for exactly this reason. Point Complianz's Privacy Statement setting at the existing page rather than leaving it as None - the banner and the Cookie Policy both link to it.

Two Complianz features need domain authentication by email, and both are easy to assume are working when they are not:

  • the Website Scan (finds real cookies on the site) - free, but capped at the first 50 pages

  • the cookiedatabase.org sync (writes the human descriptions of each cookie) - Premium only

Without the sync the Cookie Policy still generates and is accurate about what you declared, but it will not describe the third-party services you ticked, so Google Fonts and Google Maps go undocumented. Premium is per-site-count: Personal 1 site, Professional 5, Agency 25. The registration also opts the address into a marketing drip, so it is Daisy's call, not an automatic yes. Flag it; do not sign her up.

Wizard answers for a typical California local-services client:

  • Default privacy law: United States, then tick California (CPRA) under targeted states

  • Restricted log-in area: No

  • Purposes: Contact (the quote form) and Compiling and analyzing statistics (GA4). Not Payments, not Sell/share data

  • Data types - take these from the real form fields, not from habit: name, physical address (a property address for a quote), email, phone, photos if the form has an upload; plus IP address and internet activity for statistics

  • Respect Do Not Track and Global Privacy Control: Yes. CPRA expects GPC to be honoured and it costs nothing

  • Consent per Service: No. Third-party services: Yes if the site loads Google Fonts from Google's CDN or embeds a Google Map - check the logged-out HTML rather than guessing. Embedded social media: No, if the Facebook and Yelp icons are plain links rather than pixels or timelines

  • Legal Hub with Elementor Pro: No when the footer already links the legal pages, or you get a second route to the same documents

  • Finish step: Show Consent Banner Yes and Enable cookie and script blocker Yes. The blocker will replace Google Maps embeds with a placeholder until consent - that is correct behaviour, but look at those pages afterwards

Do not let the wizard put the opt-out page in the Main Menu. It offers to, and the only menu on a Kaizen build is the header nav. The CPRA opt-out link belongs in the footer with the other legal links; add it there by hand.

Complianz's own controls are custom <button> elements, not real <input>s. Scripted checks for input[type=checkbox] find nothing and read as "unselected". Read the checked state from the presence of the tick <svg> inside .cmplz-checkbox-group__item, and click by coordinate measured immediately before the click - the page reflows as answers unlock new questions, so a coordinate captured one step earlier lands on the wrong row.

California contractors must display their licence number in all advertising, websites included (B&P Code §7030.5). Take the number from the client's own email signature or an official document, verify it against the CSLB register, and never transcribe it from a photo or a scanned business card - digits get misread, and a wrong licence number on a live site is worse than none.

A licence number inside the logo image does not count as displayed. One site carried the number, the PO Box, the phone and the email as microtext baked into a 220x66 PNG - unreadable to a visitor and invisible to Google. It has to be real selectable text, and the footer under the tagline is the natural home: CA Contractors License #XXXXXXX · Licensed, bonded & insured.

Addresses on legal pages. Complianz requires an address for the documents. If the client has asked not to publish a street address, enter city, state and country only - it satisfies the field without exposing the address, and it matches what the contact page usually already says. Never invent a ZIP code to fill the box. Note that a Google Business Profile usually publishes the street address anyway, so tell the client that rather than letting them assume the address is private everywhere.

Analytics and Search Console (30 min)

  • Search Console: use a domain property, not a URL prefix. It verifies by TXT, covers www, non-www, http and https in one property, and survives the DNS cutover

  • GA4 goes in through Complianz's Statistics wizard, never Site Kit or MonsterInsights. Statistics step: "Yes, with Google Analytics"; Statistics configuration: "Yes" to let Complianz add it, then paste the Measurement ID into the Google Tag - Statistics field. Consent Mode V2 and force-in-header are Premium; leave them off

  • One GA account per client, named for the client, with the property named for the domain - matching the existing Falcon Roofing / MMT Electric / Sunwest Painting pattern. Set Reporting time zone to Los Angeles and currency USD at creation; they are a nuisance to change later

  • Business details for a landscaper: industry Home & Garden, size Small, objectives Generate leads + Understand web and/or app traffic

  • Leave "Google products & services" data sharing unticked (that is the ad-personalization one). The other three defaults are fine

  • Google will show its Terms of Service before it creates the property, and that is Daisy's to accept, not an assistant's. Hand it over rather than clicking through; tick the GDPR Data Processing Terms alongside it

  • The Measurement ID (G-…) is not the Stream ID. Open the stream, or choose "Install manually" on the Google tag screen, to read it

  • Re-check Enhanced measurement after creating the stream - it can come back switched off even when it was on in the creation flow, leaving only page views

  • Access on both GSC and GA, kept identical: [Kaizen ops Google account - ask Daisy] as Administrator / Owner (not a personal gmail), basil@kaizenagency.org and the client at Full on GSC and Editor on GA. Editor is the GA equivalent of GSC Full: everything except managing users

  • Check which Google account actually owns each property before assuming. On one build GSC ended up owned by daisy@kaizenagency.org while GA was created under [Daisy's personal Gmail]. Both worked, but nobody could remember which login opened what. Consolidate before handback

  • If the client's mailbox is Microsoft 365, their address still needs a Google account attached to it before they can actually open GSC or GA - tell them so rather than leaving a silent invitation

  • Submit /sitemap.xml only after the site is live and indexable

  • Confirm the client owns hosting, domain, email, analytics and Google Business Profile, with Kaizen as collaborator

  • Drop any orphaned *_yoast_* / *_rank_math_* tables left by plugins that were removed

Traps to check

  • Staging on *.sg-host.com burns an Elementor Pro seat; prefer staging.clientdomain.com

  • A client's live site should be its own website entry in SiteGround, never a parked domain or subdomain under a Kaizen staging plan. Parked domains alias the plan's MAIN site

  • Never use shared logins; never send passwords in Slack or email

  • Never create mailboxes on the hosting account for a domain whose mail lives elsewhere

  • A domain can have only one SPF record; merge includes, never add a second

  • Check the registrant contact email on the registrar account. If it is an address nobody can open, the account is one password reset away from being lost

  • Registrar domain lock ON except during a deliberate transfer

  • AIOSEO Pro's settings screens can render blank (its own Vue bundle throwing on mount). The plugin keeps working and keeps emitting schema - only the settings UI is dead. Reinstall the plugin rather than assuming the feature is off

  • Markdown-converting fetchers strip <script> tags, so they cannot see JSON-LD and will report "no structured data" on a site that has plenty. Check schema by reading the raw HTML for script[type="application/ld+json"], never from a text conversion

  • "X links unchecked" from Broken Link Checker means unchecked, not broken. It needs connecting to AIOSEO's service before it checks anything. Crawling the sitemap and status-checking every link yourself takes two minutes and gives a real answer

Working in the WordPress and Elementor UI

These cost real time when learned the hard way:

  • Elementor repeater items discard edits made while collapsed. Setting a link on six list items in one pass silently saves one. Expand each item, set its field, collapse it, move to the next - and verify on the front end afterwards

  • WordPress row-action links ("Move to Trash", "Edit") are hidden until the row is hovered. Clicking one programmatically does nothing and reports no error. Use the checkbox + Bulk actions + Apply path instead - or read the row's own .submitdelete href, which carries the nonce, and navigate straight to it

  • After any destructive UI action, re-read the count ("All (14) | Trash (2)") rather than trusting that the click worked. This is the same lesson as the quarantined plugin folder: the UI says done, the data says otherwise

  • In any long settings wizard, measure a control's position immediately before clicking it. Answering one question reveals or hides another and shifts everything below; a coordinate captured a step ago now lands on the neighbouring option, which looks like the click simply failed

  • Elementor's own dropdowns ignore scripted change events; set them by clicking

  • To load local text into a browser page when the media library refuses .txt uploads, inject an <input type=file> into the page and read the file with file.text()

  • Long scripted loops time out the tool call. Run them async, write results to a window variable, then poll it

  • An AIOSEO content highlighter overlay intercepts clicks in the Elementor canvas. "Disable the highlighter for this post" in its tooltip clears it for the session

Editing Elementor content programmatically

When a change spans many pages, the editor's own command API is far more reliable than clicking:

  • Open the page with ?action=elementor, wait for elementor.elements to exist, then use $e.run('document/elements/settings', {container: elementor.getContainer(id), settings: {...}}) and save with $e.run('document/save/default'). Confirm with elementor.saver.isEditorChanged() returning false

  • This path does not suffer the collapsed-repeater bug, because it writes the whole array at once

  • Walk the settings recursively. A scan of top-level string values misses most of what you are looking for. Values hide in repeater arrays (icon_list[0].link.url), in link objects (link.url), and inside raw HTML and text-editor fields. A sweep that only checks strings will report a page clean and leave two broken links on it

  • Elementor preserves widget IDs when a section is copy-pasted between pages. The same widget ID appearing on six pages does not mean it is a global widget or lives in a template, and fixing it in one place does not propagate. Confirm by checking whether the ID exists in any elementor_library template; if it does not, every page carries its own copy and every page has to be walked. Global widgets do exist as an elementor_library type of "Global Widget" and cannot be opened directly with ?action=elementor - edit them from inside a page that uses them

  • To reuse a design from another page, read the source container with elementor.getContainer(id).model.toJSON(), strip id, editSettings, defaultEditSettings and isLocked recursively, stash it in localStorage (both editors are same-origin), then recreate it on the target with $e.run('document/elements/create', {container: elementor.documents.getCurrent().container, model, options:{edit:false}}). This is how to get a new page that genuinely matches the existing design rather than an approximation - the background treatment, typography and colours all come with it. Copying a section heading this way is the quickest fix for a new widget rendering in a default colour

  • Hide the theme's duplicate page title on a new Elementor page with elementor.settings.page.model.set('hide_title','yes') before saving

  • After any batch edit, purge SG Optimizer cache, then re-crawl. If one page is clean and the rest are not, that is a data problem, not a cache problem - cache would not spare a single page
